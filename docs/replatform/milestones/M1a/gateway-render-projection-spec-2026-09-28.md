# M1a protected render projection - proposed source contract

**Status:** proposed for owner review. Not an admitted operation, campaign approval, evidence record, or change to the M1a gate.

## Purpose and boundary

The existing shipped-boot lane validates the engine's merged `docker compose config --format json` render before boot and after rollout. It applies the scoped DEP-015 invariant checker and proves that the same render fails the unscoped dispatch-default-off check. Raw render bytes may contain substituted secrets. The protected gateway must perform these checks without returning raw Compose, resolved environment values, or arbitrary validator messages to a caller.

This is the first project-wide observation needed by the approved gateway Task4/Task5 plan. It does not admit create, up, run, exec, rollout, cleanup, provider work, or live deployment. The existing logs-only gateway remains an intermediate source capability.

## Request and authority

- Add exactly one `inspect` projection value, `render`. The existing six-key request envelope remains unchanged. `arguments` is exactly `{ "projection": "render" }`; no caller paths, env, argv, project, endpoint, policy root, or selector fields are accepted.
- `services` must be the sorted, complete set from a separately reviewed **render profile**, not an empty set or a caller-selected subset. Reject duplicates, missing and extra services before invoking Compose. This declarative profile includes all merged-render services, including not-yet-created services and adapter-manager. It is signed and bound to the same controller/candidate/session, Compose hash and authority root as the execution profile; its service identities and dependency edges must agree with the execution profile where they overlap. It does **not** require container IDs and does not authorize adapter-manager execution, especially in keyless mode. The current execution profile deliberately excludes adapter-manager and requires existing containers, so it cannot be reused as the pre-boot render profile.
- Recheck the same signed authority, revocation freshness, candidate/session binding, protected profile, socket peer, fixed endpoint, and daemon continuity used for other admitted operations immediately before the render command. A successful render cannot promote a stale or test-only authority.
- Use a controller-owned, pinned Compose binary, fixed files and project. Environment substitution must come only from separately protected, reviewed session inputs; never inherit candidate/job environment or `DOCKER_HOST`. No build, pull, up, network mutation, or provider call is part of this observation.

### Pre-boot startup mode

The current `SessionRuntime` constructs an execution dispatcher and insists on an existing-container observation during gateway startup. A pre-boot render must not disable that check or seed fictional container IDs. Add a closed, independently signed `render-only` session variant with its own pinned manifest/profile schema, peer UID mapping, authority expectation and journal operation namespace. It authenticates the render profile and external launcher/custody on startup, but has **no** execution dispatcher, execution profile or container inventory requirement. Its server route accepts only `inspect/render`; every lifecycle, logs, exec/run, probe, rollout and cleanup request refuses before effect. Existing `execution` sessions retain the current signed profile and mandatory startup container inspection unchanged.

Promotion between variants is forbidden. The controller records the complete protected Compose substitution-input identity (file versions and hashes, allowlisted environment values or private value hashes, and project/overlay selection) with the pre-boot render digest. The separately reviewed **bootstrap** authority must re-render from those protected inputs immediately before its first create/up effect and require exact byte-digest equality with the committed pre-boot result. A changed input, a changed rendered byte or an unavailable comparison refuses boot until a new render, scoped check and positive control have committed a new handoff. The file hash alone is insufficient. This spec does not admit bootstrap: image pre-admission, creation, dependency and cleanup contracts remain separate required work.

After creation, a separately reviewed execution-session manifest and authority must be installed with actual independently observed container identities; it binds the same candidate/session and the verified boot render digest through a protected handoff. A caller cannot edit either handoff or reuse the render-only socket/session as a bootstrap or execution capability. A new post-rollout render may run under a separately admitted render-only observation session, with the same no-execution restriction; its digest is explicitly linked to the execution session for fresh live comparison. Distinct session-mode tags, operation IDs and journal records prevent replay across modes.

## Private render and evaluation

1. Invoke fixed `compose config --format json` with a closed argv, cwd and environment. Capture stdout/stderr privately under explicit byte and time limits. Nonzero exit, timeout, truncation, invalid UTF-8/JSON, duplicate keys, non-finite numbers, or output above the limit is `outcome-unknown` or refusal according to whether the command started. Never accept a partial model.
2. Hash the exact complete render bytes before parsing. Validate the complete service/dependency and sensitive-field shape against the independently protected profile. A render's own image, endpoint, service list or environment cannot define its expected values.
3. Run the existing `evaluateShippedBootOverlayInvariants(rendered, null, {overlayPath: SHIPPED_BOOT_OVERLAY_PATH, rendered: true})` and the unscoped `evaluateStagingManifestInvariants(rendered)` dispatch-default-off positive control on the **same captured bytes**. Use a pinned, closed verifier module and import closure. `unscopedRed` is true only when the unscoped result contains at least one `DISPATCH-DEFAULT` violation, exactly as `check-staging-manifest.mjs` does today. Unrelated unscoped violations alone never satisfy this positive control. A versioned, reviewed mapping produces stable codes; arbitrary validator prose is not returned.
4. The caller receives only a closed private result: schema version, session/operation binding, SHA-256 of exact render bytes, complete service-name set, scoped-pass boolean, dispatch-default-specific unscoped-red boolean, bounded counts and stable violation codes. It receives no raw render, env values, secret-bearing validator text, Compose stderr or host path. Any unknown violation text stays in controller-private diagnostics; admission succeeds only with scoped pass and positive-control red.
5. Do not write a resolved Compose file to the candidate workspace, public artifact, journal, console or GitHub log. If raw bytes must be retained for an evidence lane, that is a separate exact-byte inventory, private custody, retention and TK authorization decision; a hash alone is not compliant retention.

## Provenance and replay

- Extend the journal with a versioned, **render-only** closed terminal metadata variant: render digest, scoped verdict, dispatch-default positive-control verdict, bounded stable codes, render-profile hash and operation binding. The current `exitCode/resourceIDs/configHash/cleanupUncertainty` record is not silently repurposed. Existing records remain valid as their original version and are never rewritten or upgraded to render success. The new variant uses a closed marker binding the file-synced terminal record and is recovered by validated journal state, as approved in `gateway-render-durability-decision-2026-09-28.md`. A durably dispatching operation with no marker recovers unknown; a present invalid marker refuses; a valid surviving marker is re-synced and replays exact metadata with `renderAvailable: false`, never raw bytes or a fresh-render claim. Receipt of a reply is not inferred from the files.
- A post-rollout render is a new operation with a new digest. The gateway's separately admitted live-runtime projection enumerates **all** control-plane replicas and running services, and binds actual container IDs, images, startedAt, health, rollout and freeze observations to that digest before grading configured-versus-running behavior. The protected verifier evaluates the same tenant-rollout, must-be-off and freeze-exclusion semantics used by `assertTenants`; the caller gets bounded verdicts and digests, not raw environment. A clean manifest verdict alone never proves the running configuration.
- The presign probe does not receive an arbitrary raw endpoint from the caller or this projection. A separately admitted keyless probe takes its target only from the protected render's allowlisted `AOA_STORAGE_S3_PRESIGN_ENDPOINT`, binds that target to the render digest and reviewed network/CA profile, and reports the fixed HEAD probe outcome. A digest or manifest pass does not prove the probe ran.
- If the caller disconnects or the private verifier fails after command entry, retain an uncertain outcome; do not silently rerun Compose or promote a previous digest. Cleanup/reconciliation remains a separate capability.

## Required source proof

- Positive offline fixture: actual merged-render bytes pass the scoped DEP-015 checker and fail the unscoped default-off checker, with the same digest bound to both evaluations.
- Negative fixtures: missing/extra service, dependency drift, provider key on the wrong service, wrong dispatch flag, unrelated-only unscoped violations, changed overlay path, stale authority, daemon substitution, changed render between checks, malformed/oversize output, validator failure and leaked secret canary. Each refuses without publishing raw data.
- Pre-boot positive fixture includes an uncreated adapter-manager in the render profile while keyless execution still refuses it. A pre-effect re-render from identical protected substitution inputs must reproduce the committed digest; changing only a substitution input while leaving Compose files untouched refuses boot. Journal fault injection covers before/after durable terminal acknowledgement and old-record replay without promotion. Post-rollout tests compare every rendered control-plane replica with independently observed live container identities; missing, ambiguous and stale observations refuse. The presign target is not caller-selected.
- A project-wide request with a subset or arbitrary service name refuses. Two successive renders yield distinct operation identities; replay cannot masquerade as the second render. No Docker/provider/cloud operation runs in source-only tests.
- Existing `check-staging-manifest.mjs` and F3/DEP-015/E6F030 checks retain their semantics. Task5 may consume the typed verdict only after parity and negative controls prove it is equivalent to the old raw-render check, not merely because the result says `scopedPass`.

## Decisions required before implementation

TK, as accountable Integration/Security owner, must approve the exact protected Compose inputs and expected service/dependency/flag/endpoints profile, the maximum private render size and execution time, the stable violation-code set, and whether raw rendered bytes are required for later independently graded evidence. None is implicitly supplied by the historical candidate, local test fixtures, this proposal, or generic permission to keep working. The provider pre-create admission and independent retention verifier remain separate decisions.
